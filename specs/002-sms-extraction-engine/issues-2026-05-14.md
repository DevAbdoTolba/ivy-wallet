## P0-1 · Cross-wallet pending leakage

### Symptom

> *"Opened wallet num1 and synced 20 messages, mapped only 5. Opened wallet
> num2, synced 30 messages, mapped all. Messages from the sender in wallet
> num1 are appearing in wallet num2."*

Wallet 1's pending items show up in wallet 2's review or mapping screen.
Mapping a template in wallet 2 may also reprocess wallet 1's items into
wallet 2 — silent cross-contamination of accounts.

### Suspected root cause

`MapTemplateUseCase.invoke` filters pending items by **senderId** for
reprocessing, but does **not** filter by the wallet (accountId) the
template was tapped from:

```kotlin
val pending = pendingRepo.findAll().getOrNull().orEmpty()
    .filter { it.sms.senderId == updated.senderIdHint }
```

`SenderAccountLink` is 1-sender → 1-wallet on paper, but the route at
mapping time has no notion of "current wallet". If the user re-linked a
sender between wallets, or if both wallets received SMS from the same
sender at different times, the pending bucket is shared.

`PendingReviewScreen` per-wallet filtering (the wallet-scoped queue from
`002-sms-extraction-engine-ui`) only filters the **list view**; it does NOT
travel with the user into `TemplateMappingScreen` or into the save
reprocess.

### Proposed fix

1. Add an optional `walletId: AccountId?` to the `TemplateMappingScreen`
   navigation route. The wallet-scoped pending review passes it; the global
   pending review passes null.
2. `TemplateMappingViewModel.save` calls `mapTemplate(..., walletScope =
   walletId)`. When non-null, `MapTemplateUseCase` filters pending items
   by `senderId == hint AND walletId == accountResolvedFor(sender)`.
3. UX: the mapping screen shows the wallet name in its toolbar when scoped.
4. Validation: if user opens a template tapped from wallet 2's queue but
   the sender is linked to wallet 1 in `SenderAccountLink`, surface an
   error rather than silently routing into the wrong wallet.

### Files

- `shared/ui/navigation/.../TemplateMappingScreen` route definition.
- `feature/sms-sync/.../ui/nav/SmsSyncNavigation.kt`.
- `feature/sms-sync/.../ui/templates/TemplateMappingScreen.kt`.
- `feature/sms-sync/.../ui/templates/TemplateMappingViewModel.kt`.
- `feature/sms-sync/.../domain/usecase/MapTemplateUseCase.kt`.
- `feature/sms-sync/.../ui/pending/PendingReviewScreen.kt` (pass walletId
  in the navigateTo call).

### Estimate

~1 hour. Mostly threading the parameter through 4-5 hops. No DB changes.

## P0-2 · Template still shows "Needs roles assigned" after save (yet one txn lands)

### Symptom

> *"I chose a template, mapped it, loaded a little, finished to find the
> same template still waiting (Needs roles assigned). But when I check
> transactions I found one was there. Ghosting?"*

User maps a template, save reports success, ONE transaction created, but
the template card in the review queue still flags "Needs roles assigned".

### Suspected root cause

**Partial reprocess success**, not ghosting. Confirmed in the corpus test
last session — `bank-alahly-14` had 43 of 104 bodies fail alignment because
the cluster has two sub-pattern variants (different SMS formats from
different time periods) that share the same total token count and so the
auto-clusterer collapsed them into one cluster.

Save flow:
1. `MapTemplateUseCase` marks template ACTIVE, reprocesses pending items.
2. Each pending item runs `route(item.sms, template, ...)` →
   `extractWildcardValues`.
3. Items that align cleanly produce a transaction and are dismissed.
4. Items that fail alignment **stay pending** — they're still attached to
   the same template id, so the template still appears as "has unrouted
   items" in the queue.

UI sees the template still pending → labels it "Needs roles assigned"
(misleading label given the user did, in fact, assign roles).

### Proposed fix

1. **Immediate (UX clarity)**: replace the silent "convertedFromQueue: N"
   ack with a real breakdown — `1 of 10 messages were routed; 9 couldn't
   be aligned to this pattern.` Offer two actions on the screen:
   - `Edit pattern` (re-enter mapping screen for further tweaks).
   - `Dismiss the unmatched messages` (bulk-dismiss pending items that
     fail alignment against the current template).
2. **Label fix**: when the template is ACTIVE but has stuck pending
   items, the queue card says "Partially mapped — X items couldn't be
   aligned" instead of "Needs roles assigned".
3. **Structural (future)**: stricter cluster signature in
   `corpus-build.ps1` AND in production `DrainParser.descend` — use first
   ~6 stable tokens, not 3 — so sub-patterns don't share a template id in
   the first place. This was option 1 from last session, pending green
   light.

### Files

- `feature/sms-sync/.../ui/templates/TemplateMappingScreen.kt` (post-save
  UX).
- `feature/sms-sync/.../ui/pending/PendingReviewScreen.kt` (label logic).
- `feature/sms-sync/.../domain/usecase/MapTemplateUseCase.kt` (return
  `failedCount` alongside `convertedFromQueue`).
- `feature/sms-sync/.../data/DrainParser.kt` (structural fix).

### Estimate

UX label fix: ~45 min. Structural clusterer change: ~1 hour + a corpus
regen + re-annotation pass.

## P1-3 · Mapping screen shows different SMS body than the one tapped

### Symptom

> *"I opened a message saying 'charging phone wallet with 40 EGP' to map
> it. It took me to the mapping page with another message totally
> ('charging phone wallet with 89 EGP')."*

Tapping pending item A navigates to a mapping screen rendered around the
body of pending item B. Both belong to the same template, but the user
loses the SMS they were trying to act on.

### Root cause

`TemplateMappingScreen` only takes `templateId` from navigation. It looks
up `template.exampleBody` — the **first-ever sample** captured at cluster
creation time — to render the chip canvas. The actual tapped item's body
never reaches the screen.

### Proposed fix

Extend the navigation route to optionally carry the tapped pending item's
ID. The mapping screen looks up that item's body when present and uses it
as the rendered example (`displayBody`), falling back to
`template.exampleBody` otherwise. Pattern + slot roles are still derived
from the template — alignment unchanged.

### Files

- `shared/ui/navigation/.../TemplateMappingScreen` route.
- `feature/sms-sync/.../ui/nav/SmsSyncNavigation.kt`.
- `feature/sms-sync/.../ui/templates/TemplateMappingScreen.kt`.
- `feature/sms-sync/.../ui/pending/PendingReviewScreen.kt` (pass the
  itemId in `navigateTo`).

### Estimate

15–20 min. Three call-sites, one screen prop, no domain logic.

## P1-4 · Five-tap setup flow violates "speed and agility"

### Symptom

> *"In the wallet account edit, I have to click Enable → Sync now → Choose
> sender → Sync how far → Review. That's not the philosophy of the original
> designers. The app was made for speed and agility."*

### Root cause

Current SMS-sync wallet setup is a sequence of modal sheets. Each is a
separate decision point and a separate tap. The flow re-discovers state
the user already implicitly committed to by tapping "Enable".

### Proposed fix

Collapse all configuration into a **single setup sheet** invoked by the
toggle:

```
┌─────────────────────────────────────────┐
│  Set up SMS sync                        │
│                                         │
│  Sender:       [VF-Cash ▾]              │
│  Sync period:  [Last 30 days ▾]         │
│  Auto-route:   [✓ when mapped]          │
│                                         │
│  [Save & Sync now]                      │
└─────────────────────────────────────────┘
```

- Sender field default = the most-recent-SMS sender if not already linked
  to any wallet; otherwise empty (forces a pick).
- Period default = 30 days.
- `Save & Sync now` enables the wallet's SMS sync, persists sender link
  and period, and kicks off the first sync. On completion auto-navigates
  to the wallet-scoped pending review.

### Files

- `feature/sms-sync/.../ui/wallet/WalletSmsConfigScreen.kt` (collapse
  multi-sheet into single screen).
- `feature/sms-sync/.../ui/wallet/WalletSmsConfigViewModel.kt`.
- Sender picker and period picker become inline dropdowns instead of
  separate destinations.

### Estimate

3–4 hours. UX redesign + state model rewrite. Largest item on this list.
